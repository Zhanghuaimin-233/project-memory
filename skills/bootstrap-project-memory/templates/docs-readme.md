# <项目名> 文档入口

本文件说明项目文档分别负责什么、何时读取、如何创建和退出。它是文档路由，不复制各文档正文。

## 当前权威入口

| 问题 | 首选来源 | 说明 |
| --- | --- | --- |
| 项目现在是什么 | `<当前状态文档>` | 当前目标、能力、结构和限制 |
| 本次任务准备满足什么 | `<计划入口>` | 预期行为、初步接口和验收条件 |
| 哪项成熟合同需要长期独立维护 | `<Spec、Schema 或测试入口>` | Markdown Spec 不是默认产物 |
| 当前长期任务做到哪里 | `<活跃任务入口>` | State 是任务快照，不是正式规格 |
| 哪些独立后续工作尚未排期 | `<Issue 或 Backlog 入口>` | 不代表承诺、计划或实现 |
| 为什么采用或放弃某条路线 | `<知识或报告入口>` | 经验结论与完整调查证据分开 |

当文档与代码、测试或运行结果发生实质冲突时，先调查是文档漂移还是实现偏差，不直接假定任何一方正确。

## 文档类型与落位

| 信息性质 | 位置 | 命名和边界 |
| --- | --- | --- |
| 面向用户的介绍和使用 | `README.md` | 不承担 Agent 规则和完整开发历史 |
| 项目当前事实 | `<当前状态文档>` | 稳定名称；直接改写，不追加时间线 |
| 成熟系统合同 | `docs/specs/`、Schema、测试或现有等价位置 | Markdown Spec 仅在通过晋升门槛时创建；同一主题一个当前入口 |
| 任务预期与实施意图 | `docs/plans/` | `YYYY-MM-DD-任务名.md`；可含任务级要求和验收条件，不代表当前实现 |
| 活跃任务现实 | `docs/work/active/<task>/STATE.md` | 一个逻辑任务一份 State；记录当前结论和相对 Plan 的偏差 |
| 未排期的独立后续工作 | Issue 或 `docs/BACKLOG.md` | 可选单一入口；轻量记录 Bug、优化、技术债和点子 |
| 调查和验证证据 | `docs/reports/` | `YYYY-MM-DD-主题.md`；不自动成为规范 |
| 可复用经验 | `docs/KNOWLEDGE.md` 或 `docs/knowledge/` | 只记录非直观且可能复用的结论 |
| 被替代的历史 | `docs/archive/` | 默认不读取 |

只保留项目真实使用的类别。没有内容时不创建空目录。

## 新建文档规则

1. 先搜索是否已有相同主题的权威文档。
2. 能更新已有文档时，不创建“新版”“最终版”或平行说明。
3. 新文档必须能归入上表；无法归类时先说明用途，不发明新目录。
4. 未来意图必须标明 planned/proposed，不写成已实现能力。
5. 日期和修改时间不能单独决定权威性。
6. 当前任务内已解决且没有长期价值的普通 Bug 和过程交给代码、测试、Git 或会话；未排期但值得保留的独立问题按下节进入 Issue/Backlog。

## 日常事件路由

Agent 在执行中发现新信息时主动按事件判断，不等待用户指定文件类型：

| 事件 | 落点 |
| --- | --- |
| 不解决就无法满足当前目标或验收 | 当前 State；继续处理或明确阻塞 |
| 与当前验收无关、尚未排期的独立问题、优化、技术债或点子 | Issue 或单一 Backlog |
| 已决定近期实施但尚未开始 | Plan |
| 已进入实际执行 | 对应 State |
| 完整调查、实验、迁移或根因证据，未来重建成本较高 | Report |
| 可能复用但尚未成熟的经验 | State 的“候选经验” |
| 最小可独立验收范围已完成，并形成持续合同或可复用经验 | 阶段结算后进入 Spec 或 Knowledge |
| 可由代码、测试、Git 或当前会话充分表达 | 不创建长期文档 |

若 `route-project-memory` 可用则使用它；否则直接按本节执行。明确目标文件的普通编辑不重复触发路由。

## Backlog

- 优先使用项目已有 Issue 系统；只有没有合适入口且确有延期事项时才创建单一 `docs/BACKLOG.md`。
- Backlog 只保存尚未承诺立即实施、又值得避免遗忘的独立后续工作。
- 当前任务必须完成的事项留在 State，不得降级到 Backlog 后宣布完成。
- 条目被选中实施时进入 Plan，开始执行后进入 State。
- Report 保存“为什么认为问题存在”的证据；Backlog 保存“以后是否处理、做到什么算完成”。
- 完成、放弃或被替代的条目直接删除，由 Git 保存历史，不维护已完成事项墓地。

推荐最小字段：`ID、类型、事项、来源、暂缓原因、完成条件`。不要为每个条目创建独立 Markdown。

## Report 创建与检索

Report 按证据价值创建，不按任务长短创建。Bug 根因、性能或模型对比、Provider 异常、技术可行性实验、安全审计和迁移结果，如果仅靠代码、测试或 Git 难以重建，就应在调查发生时创建或更新 Report；普通小修不需要。

Report 开头应尽量提供可检索信号：

```text
状态
适用模块
相关路径或符号
错误词或主题
结论强度
当前关系：supporting / superseded
```

准备修改高风险模块、遇到非直观异常、相似错误或文档/代码/测试冲突时，按模块、路径、符号、错误词和主题搜索相关 Knowledge 与 Report。State、Knowledge 或 Spec 若长期依赖某份 Report，应直接链接它；不要要求 Agent 默认读取整个 `reports/`。

## 任务要求与稳定合同

- 当前任务的预期行为、初步接口和验收条件优先写入 Plan。
- 实施中已确认、推翻或仍待验证的结论写入唯一 State。
- State 记录任务现实和相对 Plan 的偏差，不与 Plan 并行维护第二份完整规格。
- Spec 不是默认产物。代码、Schema 和测试已充分表达行为时，不创建 Markdown Spec。
- 修改已有 Spec 的任务，在完成前由 Plan 和 State 描述拟议变化；现有 Spec 继续代表当前正式行为。

只有同时通过以下两道门槛，才创建或更新独立 Spec：

1. **持续性**：其所属的最小可独立验收范围完成后，仍被后续任务、多个模块、外部消费者、兼容或安全边界持续依赖。
2. **独立价值**：人类可读的独立文档比代码、Schema 和测试提供了额外的跨模块语义价值。

未同时通过时：

- 只服务本次任务的要求随 Plan 和 State 归档；
- 只需说明项目现状的结论进入当前状态文档；
- 可执行合同已经足够清楚时，仅维护代码、Schema 和测试；
- 非直观原因或防止重犯的经验进入 Knowledge。

## 命名规则

- 当前事实和稳定规格使用稳定名称。
- Plan、Report 使用绝对日期加主题。
- State 固定名为 `STATE.md`，任务目录使用稳定 slug，不使用会话日期。
- Archive 尽量保留原始文件名和上下文。
- 禁止 `final-new`、`v2-final`、`handoff-2` 一类通过文件名争夺权威的命名。

## 知识沉淀

- 只有根因不直观、可能复发、未来修改必须知道或容易重新采用错误路线的经验才进入 Knowledge。
- 普通小 Bug、显而易见的代码行为、未验证猜测和单次过程不进入长期知识。
- 完整现场、日志和调查证据留在 Report；Knowledge 只保留可复用结论、原因和相关入口。
- 第一次出现合格经验时才创建 `docs/KNOWLEDGE.md` 或等价文件。
- 写入前搜索并合并同主题条目，不把 Knowledge 维护成按日期追加的开发日志。
- 内容较少时按领域分节维护单文件；明显妨碍按需读取时才拆到 `docs/knowledge/`，并让 `KNOWLEDGE.md` 成为短索引。
- 通过 Spec 双门槛的正式合同才提升到 Spec；已失效的知识合并、归档或删除。

## 生命周期

```text
Plan：准备怎么做
  ↓
State：实际做到哪里、相对 Plan 改了什么
  ↓
阶段或任务完成
  ├─ 当前事实 → 当前状态文档
  ├─ 代码 / Schema / 测试已充分表达 → 不新建 Markdown Spec
  ├─ 通过持续性与独立价值门槛的合同 → Spec
  ├─ 可复用经验 → Knowledge
  ├─ 用户使用变化 → README
  ├─ 阶段结算 → 更新并保留原 State，进入下一阶段
  └─ 任务结算 → Plan / State / 过程材料退出 active
```

阶段结算只处理已经独立验收的范围，不归档仍服务长期任务的 Plan 或 State；整个逻辑任务完成后才让任务材料退出 active。会话结束但没有完成可验收范围时只更新 State，不执行结算。
