# 保存任务检查点

把未完成任务压缩成下一会话可验证、可继续的接力棒。State 是当前快照，不是会话日志、第二份计划书或完成声明。

## 完成标准

- 同一个逻辑任务复用同一份 State；
- 记录的是当前真实现场，而不是原计划或记忆推测；
- 已完成、待验证、阻塞和下一步明确分开；
- 每个仓库/worktree 的路径、分支、HEAD 与 dirty state 可恢复；
- 下一会话能从一个具体动作开始；
- 没有将中间结论提前提升到正式 Project、Spec、Knowledge 或 README。

## 1. 识别任务身份

任务身份来自长期目标，不来自会话或日期。

默认路径候选：

```text
docs/work/active/<task-slug>/STATE.md
```

优先使用项目文档合同指定的位置。若已有对应 State，必须更新它；不得创建：

```text
handoff-2.md
final-handoff.md
STATE-new.md
<date>-state.md
```

多个并行任务各自维护 State；不要把无关任务塞入一个全局 `current.md`。

## 2. 核对真实现场

写 State 前：

1. 读取项目规则、文档路由、已有 State 和相关 Plan/Spec/Report。
2. 运行适合当前环境的 `git worktree list`、`git status`、分支和 HEAD 检查。
3. 检查未提交 diff、近期提交以及本轮实际验证结果。
4. 多仓任务逐仓核对，不把一个仓库的 SHA 当成整个任务状态。
5. 只把有代码、测试、运行产物或明确用户决定支撑的事项写入“已验证完成”。

不要为了写检查点重新运行付费 provider、生产发布或高成本测试。已有验证需记录命令、结果和发生时间；没有本轮证据时写“未在本检查点重验”。

## 3. 重写而非追加

写入前完整读取 `./templates/task-state.md`，并根据项目删减。

State 至少包括：

```text
目标
当前阶段
仓库与 worktree 现场
已验证完成
当前确认
与原计划的偏差
待验证
阻塞或等待
下一步
相关入口
验证状态
候选经验
最后检查点
```

每次检查点直接删改过期内容，保持当前快照。Git 保存历史，不在 State 内追加会话流水账。

## 4. 严格区分状态

- “已验证完成”：当前现场可证明。
- “当前确认”：继续工作必须知道的稳定决定。
- “待验证”：合理但尚无充分证据。
- “与原计划的偏差”：原计划哪里失效及原因。
- “候选经验”：可能值得长期保留，但尚未完成提炼。
- “下一步”：按顺序列出可执行动作，第一项必须足够具体。

不要把候选经验写进 Knowledge，不要把开发中结论写进正式 Spec，不要归档 Plan。

## 5. 保留用户现场

检查点不改变任务授权：

- 不清理、暂存、提交或推送未完成改动；
- 不删除调试文件或中间产物；
- 不重新组织整个文档库；
- 不把“准备切换会话”解释为“任务完成”。

## 6. 验证

写入后：

1. 回读 State。
2. 对照当前 Git 状态检查路径、分支和 SHA。
3. 确认不存在同任务的第二份 active State。
4. 确认不确定内容没有写成完成事实。
5. 确认下一步无需阅读整段旧会话即可开始。
6. 向用户报告 State 路径、最后核验现场、未验证事项和下一步。
