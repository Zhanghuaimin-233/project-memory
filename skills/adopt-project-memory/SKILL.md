# 接管项目记忆

为已有项目重新建立可维护的文档秩序。优先恢复“现在从哪里开始”和“长期任务如何接力”，但优先级不代表停止点。

## 执行合同

- 下列步骤是同一次接管任务中的有序检查清单，不是可默认分别交付的多个阶段。
- 用户要求“接管”“整理”或“梳理”且没有限定范围时，连续完成所有安全、可裁决且在授权范围内的步骤。
- 不要在建立入口、创建 State 或完成盘点后，以“第一阶段已完成”作为最终答复。
- 不要求重写每份历史文档正文；但必须明确现役入口、非权威历史边界、待处理清单和仍未裁决的冲突。
- 只有用户限定了本次范围、操作需要新的授权、关键冲突必须由用户裁决，或工作确实需要跨会话时，才可以中途停止。
- 跨会话时，为文档治理任务更新同一份 State，并将交付状态标为“接管进行中”；下一会话使用 `resume-project-task` 继续，不从头重新接管。

## 完成标准

- 已确认实际仓库、worktree、规则链和文档入口；
- 已为现有文档建立职责与权威地图；
- 已建立项目级文档合同和 Agent 路由；
- 已为当前未完成长期任务建立或确认唯一 State；
- 已将无法当场裁决的冲突列为待确认；
- 大规模移动、删除和归档拥有明确预览与授权；
- 迁移后链接、索引和现役入口可用。

## 1. 盘点现实，不先整理

先执行只读调查：

1. 解析项目根、关联仓库和 worktree。
2. 读取实际生效的 AGENTS/CLAUDE、README 和文档索引。
3. 机械枚举 Markdown；先按路径、标题和链接分类，不默认把全文全部载入上下文。
4. 检查 Git 状态、近期提交、入口代码、测试与运行证据。
5. 只有发现冲突、命中当前任务或无法判断职责时才继续全文读取。

文档、日期和计划复选框都不是自动真相。代码也可能偏离既定规格；发现实质冲突时列出两边证据后再裁决。

## 2. 建立接管清单

为每份候选长期文档记录：

```text
路径
当前用途
实际类型
是否仍有效
与谁重叠或冲突
建议权威入口
建议动作：保留 / 就地改写 / 链接 / 移动 / 归档 / 删除候选 / 待确认
证据
```

清单位置按体量选择：

- 小项目可以把简短接管清单暂时放进 `docs/README.md`。
- 文档较多、迁移会跨会话或清单包含大量历史时，把完整清单放进文档治理任务的 `STATE.md` 或任务级 Report。
- `docs/README.md` 长期只保留现役路由、文档类别和少量必要的替代关系，不永久保存逐文件迁移流水账。
- 接管完成后，完整清单按项目收尾规则归档或删除，不把它提升为第二份当前事实。

使用以下语义分类，而不是机械套目录：

```text
human-entry
agent-rule
current-truth
specification
plan
task-state
  backlog
  report
knowledge
history
unknown
```

不要因为旧文档包含“必须”“验收条件”或接口草案，就机械拆出独立 Spec。先判断它是任务期预期、实施中现实还是成熟合同；只有任务结束后仍被跨任务持续依赖，且独立文档比代码、Schema 和测试更有解释价值时，才把它认定为当前 Spec。

## 3. 优先恢复入口和接力棒

先完成以下高优先级步骤，然后继续执行后续迁移：

1. 确定现有当前事实入口；没有时才创建新的稳定入口。
2. 建立或修正 `docs/README.md`、`docs/INDEX.md` 或项目等价索引。
3. 在 AGENTS 中建立短文档路由和新文档创建规则。
4. 为当前未完成长期任务建立 `STATE.md`。
5. 明确 Plans、Backlog、Reports 和 Archive 默认不代表当前实现，并把日常事件路由、Report 检索信号、阶段/任务两级结算和 Spec 双门槛写入项目文档合同。

若项目已有企划、实施手册、路线图或 architecture 各自承担明确职责，复用它们；不要为了符合模板再创建 `PROJECT.md`。

参考：

- `../../assets/templates/docs-readme.md`
- `../../assets/templates/agents-document-routing.md`
- `../../assets/templates/task-state.md`
- `../../assets/templates/backlog.md`（只有出现真实延期事项且没有 Issue 系统时使用）

## 4. 按顺序完成迁移

不要用一次大改同时重写权威内容、移动全部历史和清理工作区。
在没有停止条件时，完成一个步骤后继续下一个步骤，不把内部顺序变成多轮用户任务。

推荐顺序：

```text
冻结新的平行文档
→ 建立当前入口
→ 建立活跃任务 State
→ 逐主题裁决当前事实
→ 修复索引与链接
→ 分批归档被替代材料
→ 最后整理 README/AGENTS 重复
```

若接管会跨会话，为文档治理任务本身创建一个 State，后续更新同一文件。

## 5. 变更权限

- 在用户只要求审计或方案时，仅输出接管清单和迁移建议。
- 用户明确要求整理时，可执行范围内的就地改写和安全移动。
- 批量移动前先解析全部目标与引用，提供迁移预览；不得让仓库停在半迁移状态。
- 删除、覆盖唯一历史、跨仓移动或不可恢复操作必须遵守当前授权和项目规则。
- 不修改无关代码，不自动暂存、提交或推送。

## 6. 多仓与私有资料

项目可能把代码、私有 records、本地资产和输出分开：

- 逐仓记录路径、分支、HEAD 和 dirty state；
- 不把本机绝对路径、密钥或媒体写入公开文档；
- 代码仓的 AGENTS 必须能独立支持公开构建；
- 私有资料仓需要自己的本地入口，不能假设 Agent 总从代码仓启动；
- 跨仓链接、提交和迁移按各仓权限分别处理。

## 7. 验证与交付

完成前：

1. 回读所有受影响入口。
2. 检查索引和相对链接。
3. 搜索仍指向退役当前文档的非历史引用。
4. 确认当前事实、计划、报告和状态没有被混为同一权威。
5. 检查每个 active task 是否只有一个当前 State。
6. 输出“已建立入口、已执行迁移、待确认冲突、未处理历史”的明确清单。

最终只能使用以下一种交付状态：

- `接管完成`：所有适用的完成标准均已满足；未改写的历史已经明确为非权威资料，不再影响当前入口。
- `接管进行中`：用户明确限定了本次范围，或任务需要跨会话；必须更新治理任务的 State，列出已完成、剩余工作和下一步，不能只说某个阶段已经完成。
- `接管受阻`：存在需要新授权的操作或无法根据现有证据裁决的关键冲突；必须明确阻塞项及用户需要决定的内容。

不得将“入口已建立”“盘点已完成”或“优先步骤已完成”单独表述为整个 adopt 已完成。

一次开发任务已经完成时，不把 adopt 当成日常收尾；使用 `closeout-project-task` 执行完成态文档结算。本 Skill 不要求或调用任何外部插件。
