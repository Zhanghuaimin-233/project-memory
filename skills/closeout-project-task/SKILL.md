# 结算项目任务

在可验收边界做一次高密度文档结算：把成熟结果提升到正确的长期入口，把真正可复用的经验写入 Knowledge，并根据阶段或任务模式决定是否让任务材料退出 active。

## 完成标准

- 已用当前代码、测试、运行结果或明确用户决定确认任务或阶段确实完成；
- 当前事实、稳定规格、用户说明和 Agent 规则只更新各自必要的位置；
- State 中的候选经验已经逐条接受、合并、降级或舍弃；
- 新知识没有重复当前 Spec，也没有退化成 Bug 流水账；
- 阶段结算时仍服务长期任务的 Plan/State 已更新并保持 active；任务结算时已完成任务不再出现在 active 索引中；
- 独立延期事项已经进入 Issue/Backlog，当前目标必做项没有被错误降级；
- 所有受影响入口和相对链接可用；
- 没有清理、提交、推送或修改任务范围外的内容。

## 1. 确认完成边界

先读取：

1. 当前作用域的 AGENTS/CLAUDE 和文档入口；
2. 对应任务的 State、Plan、相关 Spec、Report；
3. 当前 Git diff、近期提交和与完成声明直接相关的测试或运行证据；
4. 本次可能受影响的当前状态文档、README 和 Knowledge 主题。

不要默认扫描全部 Plans、Reports、Knowledge 或 Archive。

先确定结算模式：

```text
阶段结算：一个最小可独立验收范围已完成，长期任务继续
任务结算：整个逻辑任务的目标和验收条件已经满足
会话结束：任务仍未完成，只应 checkpoint
```

任务长短不决定模式。长期任务可以在多个阶段边界分别结算；短任务只有形成需要同步的项目事实、成熟合同、知识、Report 或延期事项时才需要结算。

若声明完成的范围仍有影响其验收的未完成项，不执行结算；改用 `checkpoint-project-task`。与该范围验收无关的独立后续改进进入 Issue/Backlog，不能把必做项降级后宣布完成。

## 2. 建立文档影响清单

逐项判断，不要机械更新所有文档：

| 变化 | 主要落点 |
| --- | --- |
| 项目当前能力、结构、限制或近期重点 | 当前状态文档 |
| 通过持续性与独立价值门槛的成熟合同 | 对应 Spec |
| 用户可见的安装、配置或使用方式 | README |
| 所有任务都必须遵守且无法从代码推断的规则 | AGENTS |
| 未排期的独立 Bug、优化、技术债或点子 | Issue 或单一 Backlog |
| 非直观、可能复用的原因和经验 | Knowledge |
| 完整调查现场、实验数据或根因证据 | Report |
| 仅属于本次执行过程 | State、Git 或删除候选 |

同一事实只在一个主要位置维护。直接改写过期当前事实，不在旧说法后追加“现已改为”。没有实际影响的文档不要为了形式感修改。

### Report 证据

按证据价值而非任务长度判断 Report。根因调查、性能或模型对比、Provider 异常、技术可行性实验、安全审计和迁移结果，如果仅靠代码、测试或 Git 难以重建，就创建或更新 Report；普通小修不创建。

Report 应包含适用模块、相关路径或符号、错误词或主题、结论强度和当前关系等检索信号。若某项长期结论依赖它，从 State、Knowledge、Spec 或当前事实入口链接回来。

### Spec 晋升门槛

不要因为 Plan 或 State 中出现“必须”、接口草案或验收条件，就自动创建 Spec。只有同时满足以下条件，才创建或更新独立 Markdown Spec：

1. **持续性**：其所属的最小可独立验收范围完成后，仍被后续任务、多个模块、外部消费者、兼容或安全边界持续依赖。
2. **独立价值**：人类可读的独立文档比代码、Schema 和测试提供了额外的跨模块语义价值。

未同时满足时：

- 只服务本次任务的要求随 Plan 和 State 归档；
- 当前产品概况写入当前状态文档；
- 代码、Schema 和测试足以表达的合同不另建 Markdown Spec；
- 非直观原因或防止重犯的经验进入 Knowledge。

若任务修改已有 Spec，完成前以 Plan 记录预期变化、以 State 记录现实偏差；完成态核验后才更新 Spec。AGENTS 可以保留所有任务都必须遵守的简短护栏，但不能复制完整产品、数据或接口合同。

## 3. 提炼知识

先检查 State 的“候选经验”、用户纠正、返工原因、相关 Report 和代码中难以理解的约束。只有满足至少一项时才进入 Knowledge：

- 根因不直观，未来容易误判；
- 很可能在其他任务、环境或版本中再次发生；
- 用户纠正了一个具有复用价值的错误假设；
- 某条失败路线看似合理，未来 Agent 容易重新采用；
- 修复或设计选择违反直觉，单看代码难以理解；
- 修改相关模块时必须提前知道该约束。

普通拼写错误、一次性小 Bug、显而易见的代码行为、尚未验证的猜测和纯过程记录不进入 Knowledge。

### 知识落位

- 优先遵循项目文档合同指定的知识入口。
- 第一次出现合格经验时才创建 `docs/KNOWLEDGE.md` 或项目等价文件。
- 知识较少时按领域分节维护单文件。
- 已存在 `docs/knowledge/` 时，只读取和更新相关领域文件。
- 单文件明显妨碍按需读取时，才按领域拆分；让 `KNOWLEDGE.md` 退化为短索引。
- 不按日期、Bug/Decision/Failure 类型或单次任务创建零散知识文件。

### 知识条目

使用项目已有格式；没有格式时保持简短：

```markdown
## <可检索的结论标题>

**适用场景**

<什么时候需要这条经验>

**结论**

<以后应当怎么做或避免什么>

**原因**

<非直观根因、常见误判或失败路线>

**验证与相关位置**

- <代码、测试、Spec 或 Report>
```

复杂故障才补充“现象”“根因”“验证方式”。不要把完整日志和调查时间线复制进 Knowledge。

### 合并、提升和淘汰

- 写入前搜索同主题条目；更新或合并，不追加近义副本。
- 已通过 Spec 晋升门槛的正式行为合同写入 Spec；Knowledge 只保留“为什么不要走回头路”。
- 已成为所有 Agent 必须遵守的长期规则时才提升到 AGENTS，并删除重复命令式说明。
- 已失效但仍有解释价值的条目移入项目历史位置；完全没有复用价值的内容删除或交给 Git。
- 不确定的经验留在 State 或 Report，不以“可能”措辞污染长期知识。

## 4. 按模式处理任务材料

### 阶段结算

- 保留同一逻辑任务的 active State，写明已完成阶段、最新验证、当前阶段和下一步。
- 保留仍服务后续阶段的 Plan；只把已经独立成熟的结论提升到长期入口。
- 不从 active task 表移除整个任务，不归档仍在使用的 State。

### 任务结算

1. 从文档入口的 active task 表移除已完成任务。
2. 将唯一 State 移出 active 位置，使用项目合同声明的 archive/history 位置。
3. 只在 Plan 不再服务其他活跃任务时将其归档。
4. 保留仍有证据价值的 Report；不要因为任务结束就删除调查依据。
5. 更新移动导致的相对链接和索引。

没有既定归档位置时，优先建立最小且可解释的位置，不搭建空的多层归档体系。删除唯一历史、批量移动、跨仓移动或其他不可恢复操作必须遵守当前授权；无法执行时列出明确候选，不假装已经完成。

## 5. 保持边界

- 不把一次任务收尾扩大为整个文档库的重新治理；系统性混乱使用 `adopt-project-memory`。
- 不清理无关工作区、缓存、产物或用户文件。
- 不自动暂存、提交、推送、发布或创建 PR。
- 不为“显得完整”创建空 Knowledge、Spec、Report 或 Archive。
- 不要求或调用任何外部插件、MCP、Hook 或服务。

## 6. 验证与交付

完成前：

1. 回读所有修改过的文档。
2. 检查相对链接、索引和 active task 表；阶段结算必须仍保留原任务，任务结算必须移除已完成任务。
3. 搜索同主题平行当前文档和重复 Knowledge 条目。
4. 确认完成声明与当前仓库及验证证据一致。
5. 确认没有把候选经验、未来计划或 Report 误写成当前事实。
6. 检查 Git diff，只报告本次文档结算范围内的变化。

最终报告：

```text
完成依据
结算模式：阶段 / 任务
更新的当前事实、可执行合同或 Spec
接受、合并或舍弃的知识
新增或更新的 Report、Backlog/Issue
保留或退出 active 的任务材料
未执行的删除或移动候选
未验证事项和剩余风险
```
