# 恢复长期任务

使用 State 快速定位，再以真实 worktree、代码、测试和运行证据重新校准。恢复不是照抄交接文档，而是验证接力棒仍然可信后继续工作。

## 完成标准

- 找到正确的逻辑任务和唯一 active State；
- 解析每个相关仓库/worktree 的实际路径、分支、HEAD 与 dirty state；
- 标明 State 中哪些内容仍有效、已经过期或尚未验证；
- 恢复正确的下一步，而不是机械执行旧 Plan；
- 必要时先修正 State；
- 用户要求继续执行时，在原任务授权范围内进入下一步。

## 1. 选择正确的 State

读取顺序：

1. 当前作用域的 AGENTS/CLAUDE 和项目文档路由。
2. 活跃任务目录或项目声明的 handoff 入口。
3. 与用户请求匹配的 State。
4. State 直接引用的 Plan、Spec、Report 和关键代码。

不要默认读取全部 Plans、Reports、Knowledge 或 Archive。

除显式引用外，只在出现以下信号时按模块、路径、符号、错误词或主题搜索相关 Knowledge 与 Report：

- 准备修改高风险或历史问题集中模块；
- 遇到非直观异常或与历史相似的错误；
- 文档、代码、测试或运行结果互相冲突；
- State 表明某个结论依赖历史调查但链接已经缺失。

Backlog 不是恢复当前任务的默认上下文；只有 State 链接相关条目，或当前任务明确从该条目启动时才读取。

若存在多个相似 State，依据任务目标、分支、路径和最近核验时间判断；无法安全选择时向用户说明歧义，不要合并它们。

## 2. 重建真实现场

对 State 中列出的每个仓库：

1. 确认路径仍存在。
2. 运行 `git worktree list` 或等价检查，确认实现是否位于另一个 worktree。
3. 核对当前分支、HEAD、upstream 和 dirty state。
4. 阅读未提交 diff 与 State 声称的改动范围。
5. 检查 State 之后的新提交、用户改动和外部状态变化。
6. 核对关键测试或运行证据；旧的测试绿灯不得冒充当前验证。

保护已有用户改动。不要用重置、checkout 或清理命令恢复“交接时状态”。

## 3. 校准 State

将 State 中的关键断言标为：

```text
current
stale
unverified
superseded
```

若 State 已明显过期，在继续实现前先就地修正：

- 删除已经失效的“当前阶段”和下一步；
- 补入 State 之后发生的已确认变化；
- 把无法复验的完成声明降为待验证；
- 更新仓库路径、分支、HEAD 和最后检查点；
- 保持 State 为当前快照，不追加恢复日志。

## 4. 处理异常情况

### 没有 State

从项目规则、当前 diff、近期提交和直接相关 Plan/Report 重建最小检查点。若任务身份或目标有实质歧义，先请求用户方向。不要因此自动执行完整 adopt。

### State 指向不存在的 worktree

检查其他 worktree、分支和近期提交。不得擅自创建、删除或重置 worktree 来复原旧路径。

### 任务其实已经完成

不要继续执行旧下一步。报告完成证据，并使用 `closeout-project-task` 进行正式同步、知识提炼和归档；不要要求用户安装或调用外部插件。

### 外部条件已变化

依赖远端、登录态、价格、服务或生产状态时重新验证；旧 State 只能作为历史线索。

## 5. 继续任务

给出简短恢复摘要：

```text
目标
正确 worktree
当前已确认进度
State 偏差
未验证风险
下一步
```

如果用户请求“继续完成”，在原任务范围内执行第一项安全、明确的下一步。若用户只要求恢复或汇报状态，到摘要为止，不推断新的实现授权。

## 6. 验证

恢复后确认：

1. 当前目录确实是目标 worktree。
2. 未覆盖或误归属用户改动。
3. 新的下一步基于当前代码和证据，不只是旧 Plan。
4. State 已与当前现场一致，或明确标出尚未修正的差异。
5. 没有触发完成态文档提升、归档或清理。
