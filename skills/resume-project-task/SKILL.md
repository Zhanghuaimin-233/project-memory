# 恢复任务

先找到正确任务与工作现场，再决定下一步。State 是定位线索；当前目标、用户决定、代码与证据共同决定如何继续，不机械执行旧下一步。

## 用最少材料定位

从用户当前请求、适用规则和现有任务入口开始，先确认接手对象与目的。新会话本身不决定恢复哪项任务；若用户要了解整个项目而非继续旧任务，应按项目资料建立理解，不盲目执行某份 State 的下一步。

若有对应 State，读取它；若有当前 Plan，先了解目标、约束、完整剩余范围、仍影响选择的决策理由与当前步骤相关的安排，不默认吞入全部计划、报告和历史。

文档中的链接表示可查证的位置，不是必读清单。只有下一项判断确实依赖某份证据，或出现矛盾、非直观异常、历史问题信号时，再按相关模块、路径、符号或错误词读取对应章节。被替代的 Plan 不参与制定当前动作；需要追查某项决定时才查旧稿。

图表、Wiki 和知识地图也可作为入口：用它们定位当前问题涉及的关系和来源，不遍历整个知识网络。涉及具体事实时查主要资料或证据，区分用户决定、验证事实和暂定判断；漂亮的图或较新的页面不是正确性的证明。遇到源与展示版本不一致时先校准，不能据旧图行动。必要时参考 `../../assets/references/project-materials.md`；无法读取某种形式时说明缺口并找等价来源，不假称已看过。

依据任务目标、分支、路径和最近现场区分相似任务。若无法安全判断接手对象，说明具体歧义并请求方向，不把多个 State 自动合并。

没有 State 时，从当前请求、相关 diff、近期提交和已有任务材料恢复即可。能够明确继续就继续，不把补建 State、Plan 或文档体系当作前置条件。

## 核对会改变下一步的现场

- 确认正确的仓库/worktree、当前分支、HEAD 与未提交范围；多仓任务分别确认相关现场。
- 查看 State 之后与任务有关的新提交、用户改动和证据变化，保护已有未提交内容。不能用重置、切换覆盖或清理命令强行还原交接时的状态。
- 先检查未完成的外部动作或危险中间状态，例如已发送但结果未知的请求、部分迁移；查清后再决定能否重试，恢复任务不扩大原有授权。
- State 指向失效路径时，查已有 worktree、分支与提交来定位工作，不因路径变化自动重建、删除或重置 worktree。

核对程度取决于接下来要做什么。恢复记录本身不要求重新运行全部测试、重新调用付费服务或重复外部动作。

## 按变化判断证据是否仍适用

保留旧验证的原始含义：它证明了哪个提交、环境和范围。结合之后的相关代码、依赖或外部条件变化，判断它仍可支持什么，以及哪一部分需要重验。

- 没有相关变化时，可复用已有证据；不因为换会话或本次没有重跑，就把所有已完成项降回待验证。
- 变化影响某项结论时，针对受影响部分验证；验证尚未完成就明确保留该缺口，旧绿灯不能替代它。
- 找不到证据时，区分“此前声称完成”与“当前可确认”，不要凭文档勾选或记忆宣称完成。
- 外部条件决定当前动作时，只核查实际依赖的条件；旧登录态、远端或服务状态不能直接充当当前依据。

对文档与代码的冲突先查原因。代码可能是未完成实现，文档也可能过期；不能仅因一方较新就自动改变用户目标或验收条件。

## 在请求范围内继续

**用户只要求读取、评估或汇报状态时**，报告已确认现场、重要偏差和建议下一步，到此停止；不写 State，不改 Plan，不继续实现。

**用户要求继续执行时**，校准后直接推进原授权范围内下一项明确工作。已有 State 若包含会误导接手的内容，简短就地修正即可；没有必要为每次恢复新增文件或日志。

已决定的路线调整整合到当前 Plan 的相关段落，State 只保留未决问题、当前卡点和短下一步；完整剩余范围与验收条件仍在唯一当前入口维护。执行中确认的重要决定或稳定事实变化，及时同步已有资料及实际受影响的视图，不等待用户再次提醒，也不逐轮记日志。未获授权的目标或验收变化保持待决，不静默改小任务。

任务已实际完成时，停止旧的执行步骤，报告完成依据和仍需处理的具体文档差异；只在用户已有授权范围内做必要同步，不自动启动全库治理、归档或另一套 Skill 流程。

恢复摘要只说有助于用户判断的内容：正确现场、与交接不同的重要事实、未验证项和下一步。执行请求不能停在摘要后等待重复授权；真正缺少必要输入或授权时，说明受影响动作并继续不依赖它的工作。
